## 一句话理解

用户要的不是一个“看起来功能很多”的演示工具，而是一套能够交付给真实客户、在 macOS 和 Windows 上长期稳定使用的本机 Agent 工具箱：**连接、配置、补丁、模型、图片、诊断、恢复、更新和退出都必须是真的、可验证、可恢复。**

用户愿意投入时间做完整产品，但不能接受以“假成功”“编译通过”“本机偶然可用”代替真实链路验证。

## 1. 决策优先级

当功能、界面、速度、兼容性之间有冲突时，按以下顺序做判断：

1. **真实可用与数据安全。**
   - 不把 HTTP 200、空响应、缓存结果或 UI 状态当作成功。
   - 不因便于实现而读取 Cookie、会话、官方账户文件、私人数据库或其他未经明确授权的数据。
   - 不泄露 Key、Token、账号 JSON、OAuth 回调、图片数据、真实路径或未脱敏日志。

2. **不破坏已经验证的稳定链路。**
   - Antigravity 的代理、补丁、模型注入、图片、会话、端口、重试、历史和托盘逻辑是核心资产。
   - 新模块（Codex、Claude Code、Cursor、Windsurf、TOTP 等）必须隔离，不能为添加功能牺牲稳定的 Antigravity 路径。

3. **跨平台行为等价。**
   - macOS 与 Windows 可以有不同的路径、签名、安装器和系统 API；但界面语义、操作结果、错误边界、诊断能力和安全边界必须一致。

4. **清晰、克制且可操作的界面。**
   - 用户愿意接受“当前无法安全处理”的明确结果，不接受模糊、虚假的绿色状态或把内部实现细节塞给普通用户。
   - 对外显示“本地代理已启动/未启动”，不要暴露监听端口、内部 Patch ID、文件名或不必要的调试字样。

5. **效率，但不以跳过验证换速度。**
   - 可并行的工作可并行；发布、签名、安装器、Wails 绑定、实际链路验证不能假设完成。

## 2. 用户希望产品最终成为什么

### 2.1 核心定位

- 产品名称和新的可见品牌是 **XIASS Tools**。
- 它是多平台的本机 Agent 配置、连接、诊断与恢复工具，而不是通用账户接管器。
- 对客户而言，安装后应有清晰的引导、可理解的状态和可导出的脱敏诊断；对研发而言，所有关键动作应可验证、可回滚、可审计。

### 2.2 必须保持成熟的 Antigravity 能力

- 实际发现 Antigravity IDE 与 Antigravity 2.x 安装；只对已识别、已验证的结构进行最小写入。
- 支持既有/第三方/旧助手修改过的安装：先备份当前实际结构，再进行可验证覆盖或注入；失败可恢复。
- 自定义模型必须真正出现在 Agent 模型下拉框，且显示名能区分同名模型，例如：

  ```text
  gpt-5.6-sol · 供应商名/账户池名
  ```

- 显示名不得改变真实模型 ID、供应商路由或推理等级。
- 普通 OpenAI 兼容聊天默认走当前 Antigravity 可稳定使用的 Chat Completions 兼容路径；不要擅自把普通聊天改成未验证的 Responses 线路。
- Claude 必须遵守 Anthropic Messages 与 tool-use/tool-result 协议，绝不能因上下文重放、工具 ID 关联错误或自动重试导致循环回复。
- 支持文本、工具、文件拖入、截图粘贴、识图、图片显示与生成；没有真实上游能力时要明确降级，不能伪称支持。

### 2.3 图片生成的固定决策规则

1. 当聊天模型是自定义 OpenAI 兼容模型时，优先找**当前供应商/账户池组**已启用的 `gpt-image-2` 或图片模型。
2. 当前组没有可用图片模型时，才从其他已启用的图片供应商中选择。
3. 选中的图片模型必须使用其自己的上游地址与凭据。
4. 原生 Gemini 聊天模型继续走原生 Gemini 生图链路，不能错误改用 `gpt-image-2`。
5. 首次最终回复必须带有可展示的图片，不能要求用户再发一次“把图给我”。
6. 不要把 Antigravity 的 MCP rules、系统规则或工具说明误当成图片 prompt。

### 2.4 网络波动与重试的固定决策规则

- 遇到第三方 API 的偶发网络波动、短暂补号或瞬时上游不可用时，重试应针对**同一个尚未完成的请求**。
- 重试次数应在设置中可调整。
- 不隐式切换账号、不无限重放已完成回答、不把整段历史不断重新塞给上游、不制造无意义 Token 消耗。
- 重试耗尽后给出真实、可导出的诊断，而不是将客户端永久卡在 Retry 状态。

## 3. 上游、模型与账户池的产品逻辑

- 一个供应商卡片代表一个上游或账户池；卡片内部包含多个模型。
- 供应商可以编辑名称、地址、认证方式等信息；模型只处理启用、测试、删除和真实支持的推理等级。
- 用户默认只需要填写域名和必要认证信息。应用可智能补全已知 API 路径，但必须始终允许用户切换为手动完整地址。
- 同一上游可以获取可用模型、勾选若干模型、测试具体模型；测试必须实际访问当前凭据和当前协议，不能复用陈旧缓存。
- 不同登录方式只展示相关字段，避免把 OAuth、API Key、JSON 导入和 Refresh Token 的所有输入堆在同一个表单上。
- OAuth 的自动回调失败时，允许用户主动粘贴回调 URL 或 `code`；回调、state、Token 只能保留在短生命周期的本地输入状态，绝不进入日志、共享前端状态、诊断或提交记录。
- 账号等级、额度和用量只有在上游明确、实际可读取且安全时才显示；不得伪造官方账户的订阅、额度或授权状态。
- “能力声明”不应成为用户必须理解的复杂门槛；无法验证的能力可在调用时优雅降级，但不能说成已经支持。

## 4. XIASS Tools 外部集成边界

| 集成 | 用户希望实现的真实能力 | 明确不能越过的边界 |
| --- | --- | --- |
| Antigravity | 本地代理、补丁、模型、账户、图片、诊断、恢复、启动 | 不对未知二进制/ASAR/渲染器结构盲写，不保证“所有未知版本一定可补丁成功” |
| Codex | 独立 `xiass_tools` Provider、模型发现、校验备份/恢复、显式历史兼容、经过确认的 Desktop 生命周期协作 | 不读取 `auth.json`、Cookie、官方会话或伪造订阅/额度 |
| Claude Code | 标准 Gateway、`settings.json` 中用户明确的 API 根地址、Token 和模型字段、校验备份/恢复 | 不搬运外部产品的 OAuth 参数、界面、品牌或私有实现；不读取用户会话/项目设置/MCP |
| Cursor / Windsurf | 仅管理 XIASS Tools 自己拥有的 MCP 项与恢复点 | 不接管其他 MCP、账户、Cookie、数据库或任意文件路径 |
| TOTP / 2FA | 标准 TOTP、本机系统凭据库、用户主动加密导出 | 不把密钥写入 localStorage、日志、诊断、共享状态或明文文件 |

### 关于功能参考

用户希望借鉴已有 XIASS API 的成熟交互与测试逻辑；这意味着要独立实现同等的安全产品能力，而**不是**直接复制外部项目的源码、品牌、OAuth 客户端参数、图标、文案或其他受限资产。

## 5. 体验与界面偏好

- 界面是模块化、清晰、有层次的悬浮卡片设计；浅色、深色和跟随系统三种主题都必须可读。
- 字号、对比度、边框、状态色、焦点态和下拉框需要在每个主题下实际检查；不能只在开发机的一个主题中好看。
- 添加/编辑模型、账号、OAuth 等模态窗口的优先级要高，误点背景不应导致未保存内容消失。
- 第一次打开要有连续、可跳过的使用引导：

  1. 首页连接/应用 Antigravity；
  2. 跳转模型页，添加上游、获取模型、测试并添加；
  3. 回首页启动目标应用。

- 客户看到的是明确的结果、下一步和“导出诊断”；不应看到内部端口、未脱敏路径、原始响应、隐蔽实现名或混乱的多组重复按钮。
- 关闭主窗口应按系统约定最小化/进入后台；显式退出才停止本地代理并释放端口。
- macOS 须有可用的菜单栏入口；Windows 须有可用的通知区域入口；两者都可以打开主窗口和显式退出。

## 6. 研发与验收风格

### 用户最不能接受的交付方式

- “我已经修好/发布了”，但实际上只改了 UI、只编译过、没有安装器或没有跑真实链路。
- 将偶然 HTTP 200、假按钮、模拟测试、缓存成功状态写成真实成功。
- 为了新功能回归稳定功能，尤其是让 Antigravity 卡死、模型不显示、图片不展示、退出无效、配置丢失或对话循环。
- 没有区分已实测、单元测试覆盖、静态检查通过、尚待真机验证这几种不同证据等级。
- 在源码、发布物、诊断、日志、聊天或 README 中泄露敏感凭据。
- 泛泛地宣称“兼容所有版本”而没有真实结构验证；未知版本应报告其可验证事实并保持零写入。

### 用户认可的交付方式

- 先说明结果和事实依据，再说明还未验证的边界。
- 写入前预检，操作中建立受限备份/锁，原子写入并读回校验，失败时只在确实仍由本次操作写入的内容上回滚。
- 每次版本升级都同步版本号、界面、更新器、安装器、README、校验和与 Release 资产。
- macOS 必须真实打包 Universal App 和 PKG；Windows 必须由原生 Windows Runner 真实构建 Wails、生成绑定、制作并静默安装/卸载 NSIS Setup。
- 发生客户问题时优先提供脱敏诊断导出、最小复现事实和可执行修复说明，而不是要求客户反复猜测。

### 交流偏好

- 用户偏好直接、结论优先、少套话的沟通。
- 复杂任务可以并行推进，但每条工作流的验证状态必须准确，不要用“多 Agent”掩盖尚未完成的合并与验收。
- 面对不确定性，先做安全的只读检查；如果需要扩大权限、覆盖客户数据、删除发布物或做不可逆动作，必须明确说明对象、影响和恢复路径。
- 用户期待“成熟、一次到位”，但工程上应如实区分：**已验证**、**有自动测试覆盖**、**需特定环境验证**、**不支持**。

## 7. 品牌、历史兼容与发布规则

- 新产品、界面、安装包、普通诊断和新建数据使用 **XIASS Tools** 名称。
- 旧 `BYOK`、`Antigravity WF` 等标识可能是历史补丁、升级、恢复、环境变量或数据目录兼容输入；不能不加验证地全局删除。
- 正确策略：**新写入使用新品牌；旧标识只在受控兼容解析层识别，不在普通用户界面暴露。**
- Release 只保留三个正式附件：

  ```text
  macOS Universal PKG
  Windows x64 Setup EXE
  SHA256SUMS.txt
  ```

- 不发布 portable、独立 EXE、ZIP、测试构建或历史混杂附件。
- 未完成 Apple 公证、Developer ID 或 Windows 商业签名时，要如实描述 Gatekeeper/SmartScreen 影响，不能承诺无提示安装。
- 旧版本的清理与 GitHub Release 删除必须在明确确认目标和可恢复性后执行；不能用宽泛删除命令处理脏工作树。

```text

证据：具体测试、构建、安装或真实链路结果。
边界：哪些环境尚未验证，不能把它们说成已支持。
下一步：只列出必要、具体、可执行的动作。
```

如果本文件的任何条目与用户的新明确要求冲突，**以用户的新要求为准**，并把决定写回本文件，避免后续反复偏离。
